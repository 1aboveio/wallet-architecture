# Payment web SDK and iframe provider survey

Evaluated **2026-09-24 CST**, obtained with `date '+%Y-%m-%d %Z'`. Scope: official web SDKs and their browser/server boundaries; commerce plugins and the overall recommendation belong to the parent research. This is **documentation evaluation, supplemented by read-only inspection of official source code and two JavaScript bundles—not hands-on integration testing**. No SDK was mounted, credentials provisioned, payment submitted, or webhook exercised. All external sources below are first-party; citations identify the relevant page and section. Versions describe the retrieved documentation, not a guarantee about a merchant’s installed release.

## Implementation technology: JavaScript and iframes work together

JavaScript is the integration/runtime layer; a cross-origin iframe is a browser isolation boundary. These are complementary. A React wrapper controls lifecycle and props around the JavaScript API; it does not establish that the provider's hosted input UI is implemented in React. Shadow DOM isolates styling, not access by same-origin JavaScript, and cannot substitute for cross-origin isolation of card data.

The following adds public-source inspection to the documentation findings. Source on `main` is a retrieved development snapshot, not proof of a deployed production build. Braintree is checked against the specific `3.145.0` tag; its current `main` package reports `4.0.0-alpha.0`, which is not treated as a stable release.

**Design inference for this platform:** expose a framework-neutral TypeScript SDK and thin React bindings. Use provider-origin iframes for sensitive inputs, with a small typed messaging protocol that validates exact origins, source windows, instance IDs and payloads. Offer a prebuilt payment UI plus individual fields over the same payment contract. Preact is one evidenced option for the prebuilt UI, not an architectural requirement. Choose it only after measuring bundle size, accessibility and maintenance needs. Keep raw PAN/CVC out of merchant DOM, messages, logs and backend requests; supported non-sensitive state and opaque payment references can cross the boundary.

## Integration layers and credentials

“Checkout,” “session,” and “client token” do not denote interchangeable contracts. Some SDKs orchestrate payment and authentication, while others primarily exchange sensitive card details for a resource the merchant server must subsequently charge.

| Product / version boundary | Browser bootstrap and artifact | Merchant server responsibility |
| --- | --- | --- |
| **Stripe Payment Element** | Stripe.js publishable key plus either a Checkout Session client secret or a PaymentIntent client secret. The Element is a payment-method UI, not an independent payments API. | With **Checkout Sessions**, create checkout state including prices/line items and optional tax, discounts, shipping, subscriptions. With **PaymentIntents**, supply the final amount and implement surrounding checkout logic. Stripe currently recommends Sessions for most integrations. [S1][S2] |
| **Stripe hosted / embedded Checkout** | Hosted: navigate to the server-created Session’s `url`; the documented redirect integration needs no browser SDK. Embedded: publishable key plus Session `client_secret`, then mount the prebuilt checkout. | Create Session, configure return/success URLs and pricing, retrieve status, process payment events. This is a larger UI surface with less layout freedom than Payment Element. [S3][S4] |
| **Adyen Web v6 Drop-in / Components, Sessions flow** | Public `clientKey`, environment and `session: {id, sessionData}`. The client key is tied to an API credential, environment and allowed origins; it does not authenticate server API requests. | Use secret API key to call `/sessions` with merchant account, amount/currency, reference and return URL; pass session data to browser; receive outcome webhooks. Drop-in supplies the payment-method chooser; Components let the merchant place individual methods. The currently published **Standard Drop-in** guide specifically requires Web ≥6.30.0, Checkout API ≥v72 and a server library released March 30, 2026 or later; these are that guide’s requirements, not a retroactive minimum for every Sessions implementation. [A1][A2][A3] |
| **PayPal JS SDK v5 `paypal.CardFields`** | `https://www.paypal.com/sdk/js?...client-id=...&components=card-fields`; eligibility-gated number/expiry/CVV/name fields. Current single-merchant v5 guide uses client ID; the platform guide additionally supplies a server-generated `data-client-token` and merchant/partner configuration. Do not generalize that token requirement across all v5 integrations. | Keep client secret/OAuth credentials on server; `createOrder` calls Orders v2 creation and returns an order ID; `onApprove` calls server capture (or implement the appropriate authorization flow). CardFields is **not Braintree Hosted Fields** and is also distinct from PayPal’s archived `paypal.HostedFields` component. [P1][P2][P3] |
| **PayPal JS SDK v6 card fields** | `/web-sdk/v6/core`, `paypal.createInstance({clientId, components:['card-fields']})`, then eligibility and a card-fields session. This session is a browser orchestration object, not a Braintree nonce or Adyen `/sessions` response. See documentation conflicts below. [P4][P5] |
| **Braintree JavaScript v3 Hosted Fields** | `braintree.client.create({authorization})` using a server-generated client token or a static, reduced-privilege **tokenization key**; `hostedFields.create(...)`; `tokenize()` yields a payment-method **nonce**. | Use nonce in server `transaction.sale` or vaulting. ## Isolation, styling and embedding

The merchant owns the outer checkout page and the provider owns sensitive input surfaces. That boundary constrains CSS and field access; it does **not** imply that the whole checkout is one iframe, that every method uses the same frame structure, or that wrapping an SDK in another iframe is supported.

| Product | Verified boundary and customization | Outer iframe / portability limits |
| --- | --- | --- |
| **Stripe** | React reference explicitly states each Element is mounted in an iframe. Payment Element uses Appearance API themes/variables/rules; merchant CSS controls its container. Full embedded Checkout is an iframe with branding settings and more constrained customization. [S1][S3][S5] | Stripe advises avoiding an additional iframe around embedded Checkout because redirect methods may need page navigation. Hosted Checkout is a redirect integration, not a merchant-owned iframe UI. [S3][S4] |
| **Adyen** | Official best practices explicitly identify PAN, expiry and security-code inputs inside iframes. In Web v6, CSS custom properties style UI **outside** those frames; Card Component `styles` config styles secure inputs. Therefore Drop-in is not accurately described as “one iframe containing everything.” [A3][A4][A5] | Adyen discourages checkout-in-iframe; if necessary, use the same domain as parent for redirect flows. Cookie-consent blockers can prevent secure fields loading. Strict CSP can also affect issuer-hosted 3DS challenges. [A1][A4] |
| **PayPal** | v5 exposes hosted fields with supported internal CSS properties and merchant-controlled outer containers. v6 explicitly documents PayPal-hosted iframes and a field `style` object; its property schema differs from v5. Unsupported arbitrary CSS should not be assumed to pass through. [P1][P4] | The v6 SDK documents iframe-oriented integrations and presentation modes, but this does not establish identical constraints for every card, wallet, popup and redirect path. No universal nested-iframe support claim is made here. [P4][P5] |
| **Braintree** | Explicit iframe inputs for number, CVV, expiry and postal code. Merchant styles containers, including explicit heights; internal text uses an allowlisted JS `styles` object. Custom web fonts are unsupported; media queries apply to iframe dimensions, not the root window. [B1][B5] | Field isolation is documented; arbitrary nesting of the entire checkout with 3DS/wallet flows was not established by the reviewed sources. |
| **Flow** | Official customization contract is `appearance` plus `componentOptions`, including color, font and border tokens. Card detail inputs do not support custom web fonts. Official bundle contains iframe creation code, including a distinct device-fingerprint iframe; **complete per-field/frame topology was not verified**. [C5][C6] | The guide explicitly says Flow cannot be embedded inside an iframe **or Shadow DOM**. Its use of internal frames does not override that restriction. [C1] |
| **Worldpay** | Documentation separates allowlisted internal typography/color styles (web-safe fonts) from merchant CSS applied to field containers and state classes. Official Try bundle creates iframes with sources on `try.access.worldpay.com`; live DOM/frame count was not inspected. [W4][W8] | Worldpay explicitly supports a supplied `shadowRoot`, including open/closed roots, and describes an iframe workaround for nested Shadow DOM. That is a material difference from Flow; it is not proof that all downstream authentication flows work in arbitrary embedding contexts. [W5] |

**PCI qualification is not a parity metric.** Braintree and Worldpay advertise SAQ A eligibility, while the retrieved PayPal v6 card-fields reference links to SAQ A-EP. This note reports those statements without certifying compliance or inferring a universal SAQ category from “uses iframes.” [B1][W1][P4]

## Async confirmation and local status semantics

Browser “complete,” valid fields and successful tokenization describe different stages:

- **Stripe:** redirects/return pages give user feedback; fulfillment must also use server events. `checkout.session.completed` is insufficient by itself for delayed methods: inspect `payment_status`, process `checkout.session.async_payment_succeeded` / `async_payment_failed`, and make fulfillment safe for repeated/concurrent delivery. The embedded quickstart’s simplified `status: complete` success-page language must be read alongside the fulfillment guide. [S3][S6]
- **Adyen:** Sessions handles payment actions; on redirect return, rehydrate with `sessionId` and submit `redirectResult`. If the shopper never returns, the webhook still carries the outcome. `AUTHORISATION` success is authorization evidence, not proof of capture or merchant settlement. [A1]
- **PayPal:** v5 `onApprove` indicates buyer approval and triggers server capture; v6 card session `succeeded` similarly precedes capture in the documented example. Verify capture response; PayPal separately documents `PAYMENT.CAPTURE.PENDING`, `COMPLETED` and other financial events. Approval and a resolved UI promise must not be treated as settled funds. [P1][P4][P7]
- **Braintree:** a nonce represents payment information, not a transaction result. Submit it server-side, inspect transaction result/status, and handle later financial state separately. Crucially, the reviewed `transaction_settled` / `transaction_settlement_declined` webhook reference limits availability to **ACH and SEPA Direct Debit** sale/refund requests. Do not assume general card settlement webhook parity; define card status retrieval/reconciliation explicitly. [B3][B7]
- **Flow:** `onPaymentCompleted` only fires for synchronous completion; its documented status is always **`Approved`**. It does not fire when asynchronous action is needed (the reference gives 3DS as an example). Redirects and server payment retrieval/webhooks cover those paths; the guide says to wait for webhook before fulfillment. A mandate-created event is a further distinct state. [C1][C2]
- **Worldpay:** generated card session is single-use and documented as valid for **one minute**; CVC-only session is single-use for **15 minutes**. The Payments API can separately return `authorized`, `3dsDeviceDataRequired`, or `sentForSettlement`; none follows simply from obtaining a session. The integrated Payments API and older Modular APIs have different flows. Exact downstream event coverage was not evaluated here. [W2][W3][W9]

**Local interpretation, not a proposed ADR change:** [ADR 0003](adr/0003-transaction-status-model.md), especially decisions 1, 8 and 9, assigns `PAID` to authorization, `CAPTURED` to capture/clearing with net funds in `pending`, and `SETTLED` to the platform’s downstream merchant batch. Preserve provider values in `channel_raw_status`; no provider UI “success” should directly credit `available` or open the refund gate. `Order.COMPLETED` requires the capture transition. Provider capture/settlement vocabulary needs explicit adapter rules rather than string matching—especially Worldpay `sentForSettlement` and Braintree `submitForSettlement`.

An unresolved authentication or network wait can remain UI state while the submitted transaction is `PAYING`; it is not a reason to add the rejected `CAPTURING` state. Field validation/tokenization alone must not advance to `PAID`. Per [CONTEXT.md](../CONTEXT.md), use `presentment_amount` / `presentment_currency` for the capture-side monetary basis; browser configuration is not `booking_amount` or `net_settlement_amount`. These are local architectural deductions, not claims about provider APIs.

## Testing, tooling and remaining uncertainty

| Provider | Officially documented evaluation tools / test path |
| --- | --- |
| Stripe | Test cards for success, decline and authentication; delayed-method scenarios; Dashboard transaction inspection; Stripe CLI `stripe listen --forward-to ...` for local webhook delivery. [S3][S6] |
| Adyen | Test API/client keys and Customer Area, test cards/method credentials, 3DS/result-code and modification scenarios; test webhook delivery and each country/method combination. Web guidance recommends secure contexts and real mobile devices. [A4][A6] |
| PayPal | Sandbox business setup, generated test cards and sandbox account activity checks; official v5 React/vanilla samples, Codespaces/Postman links; v6 has a distinct sandbox script origin. These examples are availability evidence, not proof they were run. [P2][P5] |
| Braintree | Sandbox Control Panel, official runnable Hosted Fields tutorial, server sale results, separate 3DS guide. Current tutorial pins 3.145.0; the 3DS guide says ≥3.92.0 and 3DS `version: 2`. Old sample expiry dates must be replaced with valid test values. [B3][B4] |
| Checkout.com | Test account, `environment:'sandbox'`, downloadable sample, test cards, Dashboard payment inspection; guide requires exercising each enabled method. [C1] |
| Worldpay | Try SDK/API environment; documented cardholder-name/card-number scenarios, including `AUTHORISED`, `REFUSED`, and soft declines; outcomes depend on enabled 3DS/risk/auto-settlement features. Official React example and Payments API Postman collection. [W7][W10][W11] |

**Uncertainties to carry into implementation:**

1. **Version and documentation drift:** Stripe’s retrieved embedded guide uses `ui_mode=embedded_page` / `createEmbeddedCheckoutPage`; its current Sessions/Elements guidance uses `ui_mode=elements` / `initCheckoutElementsSdk`. Verify these names against the selected Stripe API/Stripe.js version rather than combining them with older samples. Adyen’s old `/online-payments/web-drop-in/` paths returned 404 in this pass; the current Standard guide and Card Component reference were used, with their distinct scopes recorded.
2. **PayPal v6 contradictions:** setup prose recommends client ID and says token authentication is for Fastlane, but a later parameter table still calls `clientToken` required and says 15-minute expiry while the example returns `expires_in:32400`. Follow the explicit authentication alternatives for planning; confirm the exact deployed contract and returned expiry before implementation. Do not reuse v5 identity tokens, v6 browser-safe tokens, ordinary server OAuth access tokens or Braintree client tokens interchangeably. The v5 reference labels itself CURRENT while the integration guide recommends v6 for new builds; no unsupported end-of-support date is asserted. [P1][P2][P5]
3. **No runtime parity proven:** exact iframe trees, cross-origin messaging, screen-reader behavior, font rendering, React StrictMode cleanup races, browser restrictions and latency were not tested. Static bundle inspection proves iframe creation exists, not its complete runtime security behavior. Flow’s script URL is unversioned; Worldpay’s major-version URL resolves to a minor release. Recheck dependencies at implementation.
4. **Next validation, not completed work:** exercise duplicate clicks, expired sessions, abandoned redirects, 3DS cancel/retry, SPA navigation during initialization, delayed/duplicate/out-of-order webhooks, and capture failure for each chosen product/version. There is no basis here for claiming every provider offers the same events, React wrapper, CLI, methods, credential lifetime or payment lifecycle.
