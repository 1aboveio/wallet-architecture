# Stripe Payment Element: evidence and design gaps

Scope: current first-party Stripe documentation/API references reviewed for the two **proposed**, not implemented, local contracts: [base design](payment-element-design.md) and [3DS design](payment-element-3ds-design.md). This is evidence for Explorer/Product Manager/Developer, not a product-policy decision or an internal execution-path mapping. Stripe's versioned documentation and merchant/payment-method eligibility can change; validate the selected release train and account configuration before implementation.

| Topic and Stripe evidence | What it supports; comparison with exact local sections |
| --- | --- |
| **Model and authority.** [Payment Element](https://docs.stripe.com/payments/payment-element.md#compatible-apis), [API comparison](https://docs.stripe.com/payments/checkout-sessions-and-payment-intents-comparison.md), [Checkout quickstart](https://docs.stripe.com/payments/quickstart.md) recommend Checkout Sessions with Elements (`ui_mode: elements`) for most integrations; PaymentIntents are lower-level and leave tax, shipping, discounts and checkout state to the integrator. Checkout creates a PaymentIntent on confirmation ([migration](https://docs.stripe.com/payments/payment-element/migration-ewcs.md?integration-path=one-time)). [ConfirmationToken migration](https://docs.stripe.com/payments/payment-element/migration-ct.md) is a separate *server-confirmed Intent* path: `createConfirmationToken({elements, params})`, then server confirm with `confirmation_token`; shipping/return URL can travel in the token and direct Intent parameters override them. | Base **Decision summary**, **Checkout Session contract**, **Browser SDK** choose a server-owned immutable snapshot and one session-scoped confirm. This resembles Checkout Sessions but is deliberately narrower than Stripe Checkout's mutable session features; it is not interchangeable with an Intent client secret or ConfirmationToken flow. The design does not state which feature set, mode (`payment`/`setup`/`subscription`) or server-versus-browser confirmation is supported. |
| **Eligibility and order.** [Dynamic payment methods](https://docs.stripe.com/payments/payment-methods/dynamic-payment-methods.md) default when method types are omitted on current APIs; configuration/rules and amount, currency, country, capture and future-usage restrictions filter methods, with adaptive ranking. [Payment Element options](https://docs.stripe.com/payments/payment-element.md#options) include `paymentMethodOrder`, `wallets`, layout and fields. | Base **Decision summary**, **Goals**, **Checkout Session contract**, **Lifecycle and events** promise eligible methods but do not specify configuration precedence, method capability matrix, deterministic display expectations, ordering overrides, or what happens when none qualify. In particular, manual capture and future use exclude some methods; an enabled method is not necessarily renderable. |
| **Express wallets.** [Express Checkout](https://docs.stripe.com/elements/express-checkout-element.md) has its own buttons, relevance order and browser eligibility; when combined with Payment Element, Apple Pay/Google Pay appear only in Express to avoid duplication ([Payment Element](https://docs.stripe.com/payments/payment-element.md#combine-elements)). The Checkout guide confirms with `expressCheckoutConfirmEvent`, and exposes `availablepaymentmethodschange`; shipping collection and wallet-confirm event are separate ([guide](https://docs.stripe.com/elements/express-checkout-element/accept-a-payment.md?payment-ui=embedded-components)). | Base **Merchant-owned Pay button**, **Browser SDK**, **Lifecycle and events** acknowledge method-owned buttons, but omit a separate express surface, wallet availability/empty state, wallet event handoff, wallet-sourced totals/shipping reconciliation and duplicate-wallet suppression. The standard Pay-button-only example cannot describe the express path. |
| **Saved methods, Link and consent.** Checkout can use a customer and `saved_payment_method_options.payment_method_save`; Elements can display a save checkbox and redisplay eligible saved methods, or the merchant can own that UI with explicit `savePaymentMethod`/`paymentMethod` confirmation options ([save during payment](https://docs.stripe.com/payments/save-during-payment.md?payment-ui=embedded-components)). This guide limits saved methods in this integration to cards and ACH Direct Debit and requires purpose-specific consent and retained agreement. [Payment Element](https://docs.stripe.com/payments/payment-element.md#combine-elements) says Link's legal agreement cannot be removed by the `terms` option. | Base **Checkout Session contract**, **Browser SDK**, **Secure frame boundary** leave customer identity, save/redisplay eligibility, consent record, Link authentication/autofill and legal text undefined. A browser capability limited to `confirm` does not by itself specify who may access stored methods; intentional omission if v1 is one-time guest checkout. |
| **Future use and mandates.** Checkout supports `mode: setup` ([quickstart](https://docs.stripe.com/payments/quickstart.md#handle-different-transaction-types)); save-at-payment uses explicit consent, while Intent integrations use `setup_future_usage`, with Elements options matching server Intent options ([Intent migration](https://docs.stripe.com/payments/payment-element/migration.md?integration-path=one-time)). [Payment Element options](https://docs.stripe.com/payments/payment-element.md#options) show method-specific terms/mandates when necessary; [ConfirmationToken migration](https://docs.stripe.com/payments/payment-element/migration-ct.md#optional-setting-conditional-parameters-setup_future_usage-or-capture_method-based-on-payment-method) documents per-method future-usage/capture validation. | Base **Checkout Session contract**, **Confirmation results and errors** fix amount/capture but have no setup-only session, on/off-session reuse, method-specific mandate acceptance, or legal-consent ownership. Base **Non-goals** excludes native mobile, not future payment setup, so scope is unresolved. Do not assume a universal mandate checkbox works for every method. |
| **Creation, refresh and submit.** Checkout initializes with a session secret and creates the element from Checkout ([quickstart](https://docs.stripe.com/payments/quickstart.md)); Intent path creates `stripe.elements({clientSecret})` or deferred `stripe.elements({mode,currency,amount})`, calls `elements.submit()` for validation/wallet data before `stripe.confirmPayment`, and `stripe.confirmSetup` for setup ([Intent migration](https://docs.stripe.com/payments/payment-element/migration.md?integration-path=one-time), [setup migration](https://docs.stripe.com/payments/payment-element/migration.md?integration-path=future)). The [JS reference](https://docs.stripe.com/js/elements_object/update_payment_element) distinguishes `element.update` (shallow UI option merge) from `elements.fetchUpdates()` (server Intent changes); [Elements update](https://docs.stripe.com/js/elements_object/update) notes only some options update and dahlia promises resolve after application. | Base **Browser SDK**, **Lifecycle and events**, **Checkout Session contract** specify mount/confirm/replacement but not supported UI option updates, server-data refresh, pre-confirm validation/wallet preparation, loading races, or different setup confirmation. Immutable monetary replacement is an intentional alternative to Stripe's mutable checkout/Intent amount updates, not an observed Stripe restriction. |
| **Redirect and return.** Checkout configures `return_url` with `{CHECKOUT_SESSION_ID}` ([quickstart](https://docs.stripe.com/payments/quickstart.md#supply-a-return-url)); Checkout `confirm({redirect: 'if_required'})` can keep synchronous cards on-page ([migration](https://docs.stripe.com/payments/payment-element/migration-ewcs.md?integration-path=one-time#update-the-submit-handler-client-side)). Stripe's **Intent 3DS** redirect can append `payment_intent` **and `payment_intent_client_secret`** query parameters ([3DS flow](https://docs.stripe.com/payments/3d-secure/authentication-flow.md#redirect-to-the-bank-website)). [Session object](https://docs.stripe.com/api/checkout/sessions/object) distinguishes `status: complete` from `payment_status: paid`; processing may continue. | Base **Return page and status recovery**, **Browser authentication**, 3DS **Full-page redirect or bank-app handoff**, **Return handling** intentionally forbid client secrets in URLs and require authenticated backend lookup. That is *stricter than Stripe's documented Intent redirect*, so an adapter using that path needs verification of actual return parameters and a mitigation; do not claim Stripe always returns only an opaque ID. The four local statuses are platform abstractions, not Stripe Session statuses. Redirect policy (`always` versus `if_required`) is unspecified. |
| **Events and customer data.** Stripe Elements exposes `change`, `ready`, `focus`, `blur`, `loaderror`, `loaderstart` and method-availability events ([JS event reference](https://docs.stripe.com/js/element/events/on_loaderror), [ready](https://docs.stripe.com/js/element/events/on_ready), [Express availability](https://docs.stripe.com/elements/express-checkout-element.md#check-available-payment-methods)). Checkout needs a valid email via Contact Details, session customer/email, updateEmail or confirm ([migration](https://docs.stripe.com/payments/payment-element/migration-ewcs.md?integration-path=one-time#collect-customer-email-client-side)); billing/shipping collection and updates can use separate Elements or custom forms ([address guide](https://docs.stripe.com/payments/collect-addresses.md?payment-ui=embedded-components)). | Base **Lifecycle and events**, **Browser SDK** cover core UI signals, but `loaderror`'s Stripe payload is `error` rather than a guaranteed `code/requestId`, and `actionstart/actionend` in 3DS **Action events** are *proposed platform events*, not evidenced Stripe Payment Element events. Base **Checkout Session contract** has locale but no contact, billing, shipping, phone, tax-address, delivery eligibility, or complete-data handoff contract. The design correctly refuses to treat UI events as payment truth. |
| **Visual and accessible surface.** [Appearance API](https://docs.stripe.com/elements/appearance-api.md?api-integration=checkout) offers theme, variables, public selector rules and fonts, but not arbitrary iframe CSS; it recommends at least 16px mobile input font size and provides focus/contrast variables. Stripe's [version policy](https://docs.stripe.com/sdks/stripejs-versioning.md) explicitly treats label/accessibility improvements as rolling updates. [Express Checkout](https://docs.stripe.com/elements/express-checkout-element.md#appearance) limits wallet button branding. | Base **Browser SDK**, **React binding**, **Secure frame boundary** and 3DS **Embedded or modal challenge**, **Security and privacy** mention layout/focus but leave appearance tokens, font loading/CSP, locale fallback, RTL, error announcements, keyboard navigation, contrast, zoom and merchant-owned surrounding-form accessibility uncontracted. Issuer-controlled 3DS UI cannot be themed like the element ([3DS flow](https://docs.stripe.com/payments/3d-secure/authentication-flow.md#display-in-an-iframe)). |
| **Origins, script and frames.** Stripe requires direct hosted Stripe.js loading rather than self-hosting/bundling ([JS reference](https://docs.stripe.com/js), [version policy](https://docs.stripe.com/sdks/stripejs-versioning.md)); its [security guide](https://docs.stripe.com/security/guide.md#content-security-policy) lists product-specific `script-src`/`frame-src`/`connect-src`, extra Link origins and no current cross-origin-isolated-site support. [Domain registration](https://docs.stripe.com/payments/payment-methods/pmd-registration.md?dashboard-or-api=dashboard) covers each relevant top-level/subdomain in test/live, including Connect charge ownership; outer iframe origin normally must match top origin, with Safari 17+ `allow="payment"` exception. Stripe warns against nesting Elements in another iframe ([best practices](https://docs.stripe.com/payments/payment-element/best-practices.md#integration-checklist)); manual 3DS iframes must not use `sandbox` ([3DS flow](https://docs.stripe.com/payments/3d-secure/authentication-flow.md#render-the-3ds-iframe-client-side)). | Base **Secure frame boundary** and 3DS **Security and privacy** deliberately leave exact CSP, Permissions Policy, script distribution, domain onboarding and frame modes to later testing. Stripe supports that caution, but these are launch prerequisites, not details safely left to a generic iframe policy. The local exact-origin/message protocol is a platform design, not a Stripe API guarantee. |
| **Mobile/browser.** [Express browser/WebView matrix](https://docs.stripe.com/elements/express-checkout-element.md#supported-browsers) shows method-specific support: Link/PayPal/Klarna/Amazon Pay unavailable in in-app WebViews, while wallet support is conditional (Android Google Pay host must support Payment Request API); use availability events. Stripe.js [supported browsers](https://docs.stripe.com/js/appendix/supported_browsers) and [3DS mobile redirects](https://docs.stripe.com/payments/3d-secure/authentication-flow.md#set-up-a-return-url) differentiate web, native SDK, URL scheme/universal-link handling. | Base **Non-goals** intentionally excludes native SDK; 3DS **Full-page redirect or bank-app handoff**, **Security and privacy**, **Prototype scenarios** correctly anticipate context loss but do not define supported WebViews, fallback to system browser, method filtering, app-link ownership or browser/device matrix. |
| **Server outcomes.** Checkout examples subscribe to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `.async_payment_failed`, `.expired` ([migration](https://docs.stripe.com/payments/payment-element/migration-ewcs.md?integration-path=one-time#handle-post-payment-events-server-side)); Intent examples use `payment_intent.processing`, `.succeeded`, `.payment_failed` ([Intent migration](https://docs.stripe.com/payments/payment-element/migration.md?integration-path=one-time#handle-post-payment-events-server-side)). [Webhooks](https://docs.stripe.com/webhooks.md#event-delivery-behaviors) prescribe raw-body signature verification, fast 2xx, and unordered/duplicate handling; they recommend object-ID plus event-type dedupe for distinct duplicate Event objects. | Base **Webhook authentication**, **End-to-end sequence**, **Browser and platform state**, **Return page and status recovery** already require signed, deduped, authoritative processing. Still missing an explicit public event taxonomy, method-specific delayed/failed transition examples, operational replay/reconciliation, and distinction between checkout completion and collected funds. Stripe's fulfillment examples are *not* the platform's settlement/ledger policy. |
| **Idempotency, 3DS and testing.** Stripe [idempotency](https://docs.stripe.com/api/idempotent_requests.md) replays first status/body (even 500), compares parameters, prunes keys after at least 24h, and does not save pre-execution validation/concurrency conflicts. [3DS flow](https://docs.stripe.com/payments/3d-secure/authentication-flow.md#control-the-3ds-flow) automatically handles mandates/issuer soft declines, supports Radar and `request_three_d_secure=any|challenge` on Session/Intents (issuer decides actual mode; cannot manually disable 3DS), and distinguishes `requires_action`, `requires_capture`, `processing`, `succeeded`, `requires_payment_method`; Charge `three_d_secure` is diagnostic, not payment success or guaranteed liability shift. [3DS test cards](https://docs.stripe.com/payments/3d-secure/authentication-flow.md#test-the-3ds-flow) cover required/optional/unavailable and auth-then-decline. | Base **Checkout Session contract**, **Prototype scope** and 3DS **Attempt continuity and idempotency**, **Failure and recovery behavior**, **Prototype scenarios** align on avoiding blind retry and on auth versus payment. Missing explicit 3DS request/exemption ownership, unsupported/authentication-error path, timeout/reconfirmation limits, authorization-hold expiry, proof/diagnostic fields, and live method/issuer tests. The local attempt ID and dedupe behavior are proposed guarantees, not consequences of Stripe's 24h API idempotency cache. |
| **Observability and versions.** [Best practices](https://docs.stripe.com/payments/payment-element/best-practices.md#integration-checklist) call for metadata and inspecting which methods rendered; [webhooks](https://docs.stripe.com/webhooks.md#debug-webhook-integrations) provide delivery status/replay. [Stripe.js versioning](https://docs.stripe.com/sdks/stripejs-versioning.md) is evergreen within release trains, with named breaking releases and aligned server API versions; webhook event object versions have separate handling ([webhook API versioning](https://docs.stripe.com/webhooks.md#api-versioning)). | Base **Confirmation results and errors**, **Prototype scope** and 3DS **Action events**, **Prototype scenarios** include request IDs and developer timelines. Missing production correlation schema (session/attempt/payment/event/request IDs), method-eligibility diagnostics, measurable redirect/3DS dropout and accessibility monitoring, compatibility/version policy, and sandbox-versus-live contract tests. Do not log client secrets, card data or challenge/device payloads (base **Decision summary**, 3DS **Security and privacy**). |

## Unresolved questions for owners

- **Product Manager:** Are saving/reuse, setup-only, subscriptions, optional checkout mutations, Express Checkout and embedded WebViews in scope? Which methods/markets and redirect policy are supported? The evidence above does not choose those policies.
- **Explorer:** Determine whether any *adopted* architecture or domain constraints outside the supplied proposed designs already settle these questions; this research did not explore repository implementation or internal execution paths.
- **Developer:** Validate the selected Stripe.js/API release train and account-specific eligible methods in sandbox/live, including `ui_mode: elements` versus older `custom` docs, return URL query behavior, wallet iframe/WebView support, and mandate/3DS flows. Stripe's docs contain mixed versioned examples (for example older `custom` and current `elements`, and a 3DS page with a historical 3DS1 fallback sentence alongside a notice that major brands no longer support 3DS1); do not infer a guaranteed runtime contract from those examples alone ([quickstart](https://docs.stripe.com/payments/quickstart.md), [3DS flow](https://docs.stripe.com/payments/3d-secure/authentication-flow.md), [version policy](https://docs.stripe.com/sdks/stripejs-versioning.md)).
